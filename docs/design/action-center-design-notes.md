# 行动中心设计说明 v0.1

## 页面任务

行动中心不是普通待办列表，而是把异常诊断转化为“可执行、可监控、可验证”的经营工单。它必须回答：

1. 这张工单来自哪个异常，创建时的数据证据是什么；
2. 商家决定采取什么动作，何时执行；
3. 系统接下来持续监控哪个指标、哪个 SKU 和哪个规则阈值；
4. 更新经营数据后，指标是改善、恢复、未恢复还是数据不足；
5. 工单能否关闭，以及下一周期应继续做什么。

## 核心设计：执行状态与监控状态分离

工单有两组状态，不能混为一谈：

- 执行状态：待处理、进行中、已执行、已关闭；
- 监控状态：未开始、监控中、改善中、已恢复、未恢复、数据不足。

“已执行”只表示商家做完了动作，不代表经营问题已经解决。只有完整观察窗口的数据达到恢复规则，系统才标记“已恢复”；最终关闭仍由用户确认。

## 工单与异常数据的关联

创建工单时保存不可变的异常快照：

- `findingId`、规则编码、异常标题和关联 SKU；
- 创建时的数据周期、当前值、基线值、触发阈值和证据；
- 数据范围标识 `dataScopeKey`，避免不同上传文件或演示场景串单；
- 主监控指标、改善方向、恢复规则、观察窗口和复盘日期。

后续异常即使从当前诊断列表消失，工单仍可用保存的监控口径继续评估，不能因 Finding 消失而丢失复盘依据。

## 监控与状态回写

```text
导入/更新同一数据范围
→ 前端按原口径重新聚合指标
→ 检查是否形成完整的行动后观察窗口
→ 比较当前值、创建时值和恢复阈值
→ 输出监控状态与证据
→ 写回工单时间线
```

首版状态判定：

- 数据不足：没有完整的行动后 7 个自然日，或缺少该指标所需字段；
- 已恢复：完整观察窗口内主指标不再触发原规则；
- 改善中：方向正确但仍未达到恢复阈值；
- 未恢复：无明显改善、继续恶化或观察窗口结束后仍触发规则。

规则层负责状态判定，AI 只负责解释变化、总结可能原因和给出下一步建议，不能把“改善中”改写成“已恢复”。

## 页面布局

- 页面顶部：当前数据范围、数据截止时间、创建工单入口；
- 状态概览：待处理、进行中、待复盘、已恢复；
- 全宽工单列表：支持状态、来源异常、监控结果和复盘日期筛选；
- 工单详情使用右侧抽屉：避免固定两栏造成空白，并保留列表上下文；
- 详情抽屉包括异常快照、行动记录、指标监控、规则反馈、AI 复盘和时间线。

## 创建工单

可从诊断页规则建议、AI 建议或用户自定义动作创建。必填项：

- 工单标题和关联异常；
- 行动内容；
- 主监控指标和恢复规则；
- 执行截止日期、复盘日期；
- 预计影响、置信度和执行成本，用于行动优先级排序。

首版默认带入原异常的指标和阈值，用户可以补充行动内容，但不能修改已经冻结的异常事实快照。

## MVP 边界

- 使用 `localStorage` 保存工单、状态和复盘结果；
- 支持当前浏览器内同一店铺数据范围的指标监控；
- 不做团队协作、审批、消息推送、平台自动执行和跨设备同步；
- 不因一次单日波动自动关闭工单；
- 周度复盘页面后续读取已到复盘日的工单和监控结果。

## 本轮需评审的问题

1. 执行状态和监控状态分开是否清楚；
2. “完整 7 日窗口后才判断恢复”是否符合首版预期；
3. 工单列表字段是否足够支持日常处理；
4. 右侧详情抽屉是否比固定两栏更合适；
5. 最终关闭由用户确认，还是达到恢复规则后自动关闭。
